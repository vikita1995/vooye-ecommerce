# Vooye Supabase Auth → MSG91 SMS Hook

This service receives Supabase Auth's signed Send SMS Hook and delivers the supplied OTP through MSG91's Flow API. Supabase remains responsible for generating and verifying OTPs; this service must never generate or verify OTPs itself.

## Prerequisites

- A MSG91 account with an approved OTP/transactional SMS Flow template suitable for India.
- A template whose OTP placeholder is `VAR1` (or adjust the variable name in `server.js` to match the approved template).
- GCP project `vooye-510916`, region `asia-south1`.
- Supabase project `vooye-prod` (ref `cpoitylvklkcrclsaxem`).

MSG91 may require sender/template registration and compliance approvals before Indian mobile delivery works. Confirm the current account requirements in MSG91.

## Runtime secrets

Create these Secret Manager secrets without putting their values in GitHub:

- `msg91-authkey`: MSG91 API auth key.
- `msg91-template-id`: approved MSG91 Flow template ID.
- `supabase-send-sms-hook-secret`: the full Supabase hook secret in the form `v1,whsec_<base64-secret>`.

Grant the Cloud Run runtime service account access to these three secrets only. The service uses environment variables `MSG91_AUTHKEY`, `MSG91_TEMPLATE_ID`, and `SUPABASE_SEND_SMS_HOOK_SECRET`.

## Build and deploy

Run from the repository root in Cloud Shell. These commands do not print secret values:

```bash
gcloud config set project vooye-510916
gcloud services enable run.googleapis.com cloudbuild.googleapis.com secretmanager.googleapis.com
gcloud builds submit vooye-production/sms-hook \
  --tag asia-south1-docker.pkg.dev/vooye-510916/vooye-services/vooye-msg91-sms-hook
```

Create the Artifact Registry Docker repository once if it does not exist:

```bash
gcloud artifacts repositories create vooye-services \
  --repository-format=docker --location=asia-south1 \
  --description="Vooye service images"
```

Deploy after the image has been built and the three secrets have been created:

```bash
gcloud run deploy vooye-msg91-sms-hook \
  --image asia-south1-docker.pkg.dev/vooye-510916/vooye-services/vooye-msg91-sms-hook \
  --region asia-south1 \
  --service-account vooye-runtime@vooye-510916.iam.gserviceaccount.com \
  --no-allow-unauthenticated \
  --set-secrets MSG91_AUTHKEY=msg91-authkey:latest,MSG91_TEMPLATE_ID=msg91-template-id:latest,SUPABASE_SEND_SMS_HOOK_SECRET=supabase-send-sms-hook-secret:latest
```

Supabase HTTP hooks need to call the endpoint. For Cloud Run, the request must be authenticated; configure a supported authentication path that Supabase can use, or put a narrowly scoped authenticated gateway in front of Cloud Run. Do not make the service publicly invokable without validating the signed Supabase webhook. The code validates the webhook signature, but Cloud Run IAM authentication is a separate layer and may not be directly compatible with Supabase's HTTP hook caller.

After deployment, retrieve the service URL with:

```bash
gcloud run services describe vooye-msg91-sms-hook --region asia-south1 --format='value(status.url)'
```

The hook path is `/hooks/supabase/send-sms`.

## Configure Supabase

1. In Supabase Dashboard → Authentication → Sign In / Providers → Phone, enable Phone.
2. Keep SMS auto-confirmation disabled so OTP verification is required.
3. Open Authentication → Hooks and configure the **Send SMS** HTTP hook to the deployed URL plus `/hooks/supabase/send-sms`.
4. Use the exact signing secret generated by Supabase for the hook; store it in Secret Manager as above.
5. Save and test using a phone number you control. Verify successful delivery and the subsequent six-digit code verification in Vooye.

## Important notes

- Never commit API keys, hook secrets, OTPs, or customer phone numbers.
- Restrict SMS destinations/rate limits in Supabase Auth and MSG91 to control abuse and cost.
- MSG91 Flow API uses `template_id`, `recipients[].mobiles`, and `VAR1`; make sure the registered template matches.
- The service deliberately does not log request payloads, phone numbers, OTPs, API keys, or provider response bodies.
- `/healthz` is a basic liveness endpoint and does not prove MSG91 credentials or delivery work.
